Qualtrics → LimeSurvey

A free tool that converts a Qualtrics survey export (.qsf) into a file you can import into LimeSurvey (.lss). It saves you rebuilding the survey by hand. You'll still need to check the result.

Opening it the first time: on Windows, click More info → Run anyway if a blue warning appears. On a Mac, right-click the app → Open → Open. The program isn't code-signed yet, see code signing policy.

Made with AI: this website and the converter's code were created by AI (Claude, by Anthropic) based on an idea by Konrad Schweizer. The screenshots come from the real program; the demo survey is made up. Spotted a mistake? Tell us on GitHub.

How to use it

  1. Export your survey in Qualtrics: Tools / … menu → Export survey → QSF.
  2. Open QSF2LSS-GUI and drag the .qsf file onto the window.
  3. Convert. Press Convert and read the checks. Amber lines show what to look at.
  4. Import the .lss in LimeSurvey: Create survey → Import. Then test the survey before using it.

Export your survey from Qualtrics

2

Start QSF2LSS

Download the zip for your computer from the buttons at the top, unzip it anywhere and start QSF2LSS-GUI. It opens one window. There is a drop zone at the top, a file list on the left, a details pane on the right and the controls along the bottom.

  • WindowsDouble-click QSF2LSS-GUI.exe. If SmartScreen warns you, click More info → Run anyway (the exe isn't code-signed).
  • macOSThe first time only, right-click QSF2LSS-GUI.app → Open → Open. This clears Apple's “unidentified developer” warning.
3

Drop in your .qsf files

Drag one or more .qsf files, or a whole folder, onto the window. The drop zone lights up while you drag. If you drop a folder, it is searched recursively and every .qsf inside is added. Anything that isn't a .qsf is ignored. If you'd rather not drag, click the drop zone or use Add files… / Add folder….

4

Check the queue and choose where the output goes

Each file appears in the list with the status Ready. By default each .lss is written next to its .qsf. Click Change… to send everything to one folder instead. Select a file and press Delete (or Remove) to take it off the list, or press Clear to start over.

5

Press Convert and read the result

Press Convert. Every file is inspected, converted and verified in the background, so the window stays responsive even for large batches. Each row then gets a coloured verdict: green OK, amber OK with warnings or red failed. Click a row to see its details.

The details pane has three parts:

  • Input (Qualtrics)Survey name, language, 13 questions in 5 blocks, a breakdown by question type, and the detected features: display logic, piped text, JavaScript, embedded data. It also shows a migration risk score.
  • Output (LimeSurvey)What was written: 4 groups, 12 questions, 7 subquestions (array and ranking rows) and 22 answer options, broken down by LimeSurvey question type.
  • VerificationTen checks that compare input and output (scroll down, Fig. 5).

Then, in LimeSurvey:

  1. Open the LimeSurvey admin panel and click Create survey.
  2. Switch to the Import tab, choose the .lss file and click Import survey.
  3. LimeSurvey shows an import summary (groups, questions, answers). Compare it with the “Output” numbers in the report.

Review checklist before you activate

  • Click through every question group and check that the questions look right.
  • Check that answer options and subquestions are complete and in the right order.
  • Preview the survey and trigger each display-logic condition.
  • Search the survey for FIXME. These mark expressions that need a manual fix.
  • Add embedded data fields as URL parameters (Survey settings → Panel integration).
  • Rebuild any custom JavaScript and timing behaviour you still need.
  • Run the whole survey once from start to finish, then activate it.

Prefer no clicking? The download also includes QSF2LSS, a folder-based version. Put .qsf files in input/, double-click it, and collect the results from output/.

How it works

For the curious. In short, the tool inspects the Qualtrics file, converts each block, question, answer and logic rule into LimeSurvey's format, and then verifies the result by comparing the two files.

Technical details: pipeline, conversion rules, checks

A .qsf file is JSON: a SurveyEntry with metadata plus a flat list of SurveyElements (BL blocks, FL survey flow, SQ questions, SO options). A .lss file is XML that mirrors LimeSurvey's database tables.

Inspect

qsf_inspector.py
  • Reads the QSF and counts questions, blocks and types
  • Finds display logic, validation, piped text, JavaScript, randomisation, branches and embedded data
  • Flags problem and unmapped types
  • Computes a migration risk score

Convert

qsf_to_lss.py
  • Orders blocks using the survey flow
  • Blocks → groups, questions → typed LimeSurvey questions
  • Choices → answers or subquestions
  • Logic → relevance, piped text → expressions
  • Writes the LSS XML

Verify

app.py · gui.py
  • Parses the .lss it just wrote
  • Runs 10 checks comparing input and output
  • Writes a timestamped report and shows it on screen

Stage 1: inspection and the risk score

Before anything is converted, the inspector reads every question and survey element and builds a profile of the survey. This is what appears under Input (Qualtrics). From that profile it computes a simple migration risk score. It's a rough guide to how much manual work to expect, and it's most useful for sorting a batch of surveys so you tackle the hard ones first.

A “problem type” is a Qualtrics question with no clean LimeSurvey equivalent: heat maps, hot spots, timing, captcha, file upload, meta info and similar. A type is “unmapped” if it isn't in the inspector's list of known-safe mappings.

Stage 2: conversion, piece by piece

The converter builds the LimeSurvey tables one row at a time. Pick a topic to see what happens to it. The “before” and “after” snippets are taken from the demo survey's real input and output.

Qualtrics stores blocks in one BL element and their order in the FL (survey flow) element. The converter walks the flow tree from top to bottom, including blocks nested inside branches and randomisers, and records each block the first time it appears. Blocks that exist but never appear in the flow are added at the end, so nothing is lost.

Each remaining block becomes a question group in that order. The block's description becomes the group name. Blocks named Trash or Unused and empty blocks are skipped. Groups, questions and the survey get new sequential IDs (sid 100000, then gid 1, 2, 3… and qid 1, 2, 3…). Qualtrics' DataExportTag becomes the LimeSurvey question code, so your variable names stay the same.

Every Qualtrics question has a QuestionType and a Selector, the visual variant. The pair is looked up in a mapping table to get a one-letter LimeSurvey type code. If the exact pair isn't there, the type is tried on its own (so DB/GRB still becomes Text Display). Anything still unknown becomes T (Long free text) with a warning, so the question text is never lost. The full table is below.

Qualtrics question

  "Selector":      "MAVR",   // multi-answer, vertical

Qualtrics stores options as Choices, plus Answers for matrix scale points, each with a ChoiceOrder. LimeSurvey splits options into two kinds, so the converter decides by target type:

  • Answer options for lists, dropdowns and multiple choice (L ! M). Each choice becomes an answer coded A1, A2, … in the original order.
  • Subquestions for arrays, ranking and multiple numerical (F ; 1 K R). Each choice becomes a row coded SQ001, SQ002, … For Likert and bipolar matrices the Qualtrics Answers (scale points) also become answer options, i.e. the array's columns.
  • A single-choice question with a text-entry choice (“Other: ____”) gets LimeSurvey's built-in Other option switched on.
Qualtrics Matrix / Likert
"Choices": {            // statements (rows)
  "1": "Coffee helps me concentrate",
  "2": "I drink coffee mostly out of habit",
  "3": "I would like to drink less coffee" },
"Answers": {            // scale (columns)
  "1": "Strongly disagree", … "5": "Strongly agree" }
LimeSurvey array (F)
question  attitudes   type F
├─ subquestion SQ001  Coffee helps me concentrate
├─ subquestion SQ002  I drink coffee mostly out of habit
├─ subquestion SQ003  I would like to drink less coffee
└─ answers A1…A5      Strongly disagree … Strongly agree

Qualtrics display logic is a nested tree of If/Expression nodes. The converter walks the tree and turns each condition into an ExpressionManager term, using the referenced question's export tag. It supports Selected and NotSelected, EqualTo and NotEqualTo, greater/less than (or equal), IsEmpty/IsNotEmpty, IsDisplayed/IsNotDisplayed, and Contains/Matches (as regexMatch). The terms are joined with && and written to the question's relevance field. A question without logic gets relevance 1 (always shown).

Where you'll need to step in: conditions are always joined with AND. Logic that relies on OR, on nested groups, or on an operator the converter doesn't recognise gets a /* FIXME … */ marker instead of a guess. Search the survey for FIXME after importing, and test every condition in preview.

Piped text inserts earlier answers or variables into question text. The converter rewrites it in question text, answer labels and subquestion labels:

Mandatory: a Qualtrics question with ForceResponse = ON is written with mandatory = Y. Other validation (content type, regex, min/max characters) is counted in the report but not carried over.

Sliders become numerical input (N). The slider's range is kept as question attributes, so you can switch the question to LimeSurvey's slider display and keep the original scale.

Finally, the rows are serialised as a LimeSurvey 5.x structure document (DBVersion 500), one XML section per table. The survey's title and language come from the QSF, and the new survey starts inactive so you can review it first. The XML is written in UTF-8, and HTML in question text is escaped so formatting survives the round trip. The converter uses only Python's standard library (json, re, xml.etree).

<document>
  <LimeSurveyDocType>Survey</LimeSurveyDocType>
  <DBVersion>500</DBVersion>
  <languages><language>EN</language></languages>
  <surveys>…</surveys>                      <!-- settings, title -->
  <surveys_languagesettings>…</surveys_languagesettings>
  <groups>…</groups>                        <!-- one row per block -->
  <questions>…</questions>                  <!-- type, code, text, relevance, mandatory -->
  <subquestions>…</subquestions>            <!-- array / ranking rows -->
  <answers>…</answers>                      <!-- answer options, A1 … An -->
  <question_attributes>…</question_attributes>
  <conditions/>
</document>

Stage 3: verification

The converter doesn't just trust itself. After writing the .lss, the app parses it again and compares the result with the inspection from Stage 1. A count that doesn't match isn't automatically a bug, because some differences are expected. The checks are there so that no difference goes unnoticed.

#CheckComparesCan be
1Question countSQ elements in QSF vs. question rows in LSSOK !!
2Group countQualtrics blocks vs. LimeSurvey groupsOK !!
3Type coverageEvery type/selector pair has a mappingOK !!
4Answer optionsQSF choices vs. answers + subquestions (within 10% counts as OK)OK !!
5MandatoryForceResponse=ON vs. mandatory=YOK !!
6Display logicQuestions with logic vs. questions with a relevance equationOK !! FAIL
7Conversion warningsWarnings raised by the converter (e.g. unmapped types)OK !!
8Problem typesTypes with no clean LimeSurvey equivalent!!
9JavaScriptQuestions with custom Qualtrics JS!!
10Embedded dataFields to set up as URL parametersi

Overall verdict per file: any FAIL → “check(s) failed”, otherwise any warning → “OK with warnings”, otherwise “OK”. If the conversion itself throws an error, it is caught, shown for that file and written to the report, and the remaining files carry on.

Known limitations

  • Timing questions become display-only placeholders.
  • Custom JavaScript isn't transferred.
  • Complex display logic (OR, nested groups) may come out simplified or with FIXME markers.
  • Block randomisers are detected but not turned into LimeSurvey randomisation groups.
  • Loop & merge piped text becomes FIXME_LOOP_REF.
  • Side-by-side questions become a single array as a best-effort approximation.
  • Validation beyond force response isn't carried over.
  • Count differences between input and output are often expected (trash blocks, matrix rows).

Questions & troubleshooting

Do I need Python?
No. The downloads bundle everything. If you prefer to run from source: Python 3.10+, then python source/gui.py (window) or python source/convert.py input/ -o output/ (command line). For drag & drop, also run pip install tkinterdnd2. Without it, the drop zone works as a click-to-browse button.
Windows says “Windows protected your PC”
The exe isn't code-signed yet (see code signing policy). Click More info → Run anyway. If you'd rather not, run from source or build it yourself; the GitHub Actions workflow in the repository shows exactly how the release builds are made.
macOS says the app “cannot be opened”
Right-click (or Control-click) the app → Open → Open. You only need to do this once. If it's still blocked, go to System Settings → Privacy & Security and click Open Anyway.
The window doesn't open or closes immediately
Run the console version QSF2LSS instead. It prints any error message, or run python source/gui.py from a terminal to see the full error.
Why does the question count differ?
Usually it's expected. Questions in the Trash block aren't converted, and the inspector counts every question element, including unused ones.
Can I convert many surveys at once?
Yes. Drop a whole folder onto the window, or put all files in input/ for the folder-based version. One report covers the whole batch.
